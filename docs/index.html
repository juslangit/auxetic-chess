Auxetic Chess

Normal chess with one twist: after every move, all sixteen 2×2 blocks of the board turn a quarter and carry the pieces standing on them, so the position keeps getting scrambled — a4 becomes b4, one cell round the block, pawns included. A pawn only ever moves forward, never sideways or backwards, but the board will carry it anywhere. It is the default game, not an option. The board is also a rotating-squares auxetic mechanism — sixteen rigid tiles, hinged at their corners, that bloom open to exactly twice their area and close into a solid 8×8 to play on. Built after a 3D-printed physical board by Ruven Bals, which Luqman sent over as a video on 2026-09-12; the twist was his own idea, added 2026-09-13.

Why this project exists

Luqman sent a video of a 3D-printed folding chess board and asked for the game. The interesting part is not chess — it is the mechanism. A rotating-squares auxetic lattice has a negative Poisson's ratio: pull it on one axis and it grows on both. Rendering that honestly, from the kinematic constraint rather than a tween, is what makes the piece worth showing.

What counts as "done"

  1. Legal chess, with no exceptions — castling, en passant, promotion, and every draw rule. Verified by perft, not by eye.
  2. The fold is derived from the hinge constraint, so the tiles stay joined at every angle.
  3. An opponent worth playing, and four strengths so it is not only for one level.
  4. Playable on a phone as well as a desktop.
  5. The twist is a real mechanic, not decoration: it lives inside the engine, so the search plays the variant properly, and it can never freeze the game (added 2026-09-13, D-006/D-007).

All five hold as of 2026-09-14.

The twist, in one line

Each block cycles its contents a1→a2→b2→b1 — so a4→b4 — for every piece. It can never capture, nothing leaves or enters a block, four turns is the identity, and the whole thing stands down on any turn where turning would expose the mover's king. A pawn's own moves stay forward-only regardless of where it is carried.

The fold, in one line

For the corner hinges to stay joined, tile pitch is fixed by the rotation: d = a·√2·cos(45° + θ), with tiles alternating +θ / −θ in a checkerboard. θ = 0° is the solid playable board; θ = −45° is fully bloomed at exactly 2× the area.

D-001 — Digital game, not a printable model
  • Date: 2026-09-12
  • Status: active
  • Context: The source video is a physical 3D print. "Make this chess game" could mean model it for the BambuLab or build a playable game. The two share almost no work, so it had to be settled before starting.
  • Options considered:
OptionProsCons
Printable STLsMatches Luqman's hardware and 3D skillHinge tolerances need several test prints; not playable
Digital gamePlayable, shareable, portfolio-readyDoes not use the printer
BothGeometry carries overMuch longer
  • Decision: Digital, playable, in the browser. Luqman chose it directly.
  • Consequence: The parametric tile/hinge model is still unbuilt. If it is wanted later, the geometry in js/board.js is the starting point.
D-002 — Expansion direction, not collapse
  • Date: 2026-09-12
  • Status: active
  • Context: d = a·√2·cos(45°+θ) is valid for θ either side of zero. θ > 0 collapses the board toward a point (how you pack the real one away); θ < 0 blooms it open into a lattice. Only one could be the animation.
  • Decision: Use the expansion direction, θ from −45° to 0.
  • Reasoning: At θ → +45° the pitch goes to zero, so in a flat 2D render the tiles interpenetrate and read as a muddle — the physical board only survives it because tiles stack in the third dimension. The expansion direction has no overlap at any angle, doubles the area, and is the actual auxetic signature worth showing.
  • Consequence: A new game blooms closed into play; the end of a game blooms it back open. A "pack away" animation would need real 3D.
D-003 — One baked tile sprite for all sixteen
  • Date: 2026-09-12
  • Status: active
  • Context: Drawing each tile's checkerboard, bevel and hinge pins live cost 4 fps, because ctx.filter = blur() per tile per frame is ruinous.
  • Decision: Bake the tile body, the hinge pin, the backdrop and every piece into offscreen canvases once, then blit.
  • Reasoning: Every tile carries the same 2×2 patch. A tile starts on an even file and even rank, so its local colour parity is (u+v)%2 whichever tile it is — and that parity is unchanged by flipping the board. One sprite therefore serves all sixteen, in both orientations. This is the same fact that lets the physical board be printed from a single tile model.
  • Consequence: 4 fps → 54 fps under headless software rendering. Only live state (selection, legal dots, check, last move) is painted per frame.
D-004 — Search runs on the main thread, inside a time budget
  • Date: 2026-09-12
  • Status: active
  • Context: A Web Worker would keep the UI responsive while the engine thinks.
  • Decision: No worker. Search synchronously with a per-level time budget (120 ms to 4 s), yielding one frame first so "Thinking…" paints.
  • Reasoning: Chrome blocks blob: workers from a file:// origin, so a worker version would only run from a server. Opening index.html directly had to keep working.
  • Consequence: The tab is blocked for up to ~4 s on the Brutal level. If online play is ever added, revisit this with a proper server-served worker.
D-005 — The table turns a quarter after every move
  • Date: 2026-09-12
  • Status: reversed 2026-09-13 — superseded by D-006. This was a misreading of what Luqman asked for. He wanted a game mechanic that scrambles the position; I built a cosmetic whole-table spin. The code was removed rather than left switched off, so it would not fight the real mechanic. Kept here because the two lessons in it still hold: rotating a playable board means inverting the input, and a transition has to be atomic or input leaks into the pause.
  • Context: Luqman asked for the board to rotate itself 90° once a player finishes a turn, so it comes round to face the other side.
  • Decision: A whole-board rotation applied as a transform on the way to the screen, kept separate from the logical file/rank mapping that flipped uses. On by default, with a Spin table toggle.
  • Reasoning and the three things it forced:
    1. Input has to be un-rotated. A click is mapped back through the inverse rotation before it is read as a square. This is the part that actually breaks, so it is tested at 0/90/180/270° and with the board flipped.
    2. The board must shrink mid-turn. A square of side L rotated by φ has a bounding box of L·(|cos φ| + |sin φ|), 1.41× at 45°. The board is already 0.86 of the stage, so a naive quarter turn throws the corners off screen. Scale backs off by min(1, (0.98/0.86)/(|cos φ|+|sin φ|)) — 1 at every rest position, ~0.81 at the midpoint, peaking at 98% of the stage. It reads as the board lifting slightly as it turns.
    3. The turn must finish before the engine thinks. The search blocks this thread (D-004), so starting it mid-rotation freezes the animation halfway. advanceTurn awaits the spin, then hands over.
  • Pieces do not turn with the board. Five of the six types are lathe shapes and look identical from any direction, so keeping them upright is what actually happens to the real turned pieces when the table spins under them. It also keeps the knight readable, which a 90° roll would not.
  • Consequence: At 90° and 270° the board is side-on, with White's back rank on the left. That is inherent to a quarter turn and is what was asked for; a half turn would be the "face the opponent" version if that is ever wanted.
D-006 — The twist: every 2x2 block turns a quarter, carrying the pieces
  • Date: 2026-09-13
  • Status: active
  • Context: Luqman, after D-005 went the wrong way: "the game will be play as normal chess gameplay but i want to add a twist to make it interesting by making 2x2 of the square rotate 90 degree after a turn from the player so the chess board will be abnormal ... i want the rotate to be the game mechanics soo it will rotate automatically." Asked which block; answer: all of them.
  • Decision: After every move, all sixteen blocks turn a quarter and carry whatever stands on them. Inside a block the contents go (u,v) -> (v, 1-u), i.e. a1→a2→b2→b1→a1, period 4.
  • Why it runs inside make: because "all blocks" is deterministic, the twist could go in the engine's own make/unmake rather than being layered on top. Move generation, check detection, checkmate and the entire search then see the variant for free, and the AI plays it properly instead of playing normal chess into a scrambling board. This was the single most valuable consequence of the rule being deterministic, and it is why the block choice was worth settling before writing any code.
  • Properties that fall out of it being a permutation of four squares: a twist can never capture; nothing ever leaves its own block; four turns is the identity.
  • Consequences accepted: en passant never arises (a double push cannot be answered once everything has moved); castling rights lapse as soon as a twist carries the king off e1, so castling effectively does not occur; a pawn carried onto the far rank auto-promotes to a queen, with no choice offered because it is nobody's move.
D-007 — The twist yields, not the player
  • Date: 2026-09-13
  • Status: active
  • Context: The first rule tried was the principled one — your move must leave your king safe after the twist — enforced for free by the existing legality test. It deadlocks. The permutation does not depend on what you play, so a king hemmed in by its own pieces is carried onto the same square every time; if that square is covered, every move is illegal. Self-play drew by stalemate on move 3: White's king on e1 always carried to e2, a black queen on d4 always carried to d3, which covers e2. Confirmed by dumping the position rather than assuming it was a bug.
  • Decision: If turning the board would walk the mover's own king onto an attacked square, it does not turn that turn.
  • Reasoning: It keeps normal chess legality exactly — the twist can never take a move away from you, which is asserted directly against a twist-free clone across 160 positions — so the game cannot freeze. It stays deterministic, so it still lives inside make (D-006). And it is one sentence to explain.
  • Measured: it stands down on roughly one turn in seven (24 of 160).
  • Rejected: letting the twist leave your own king attacked and treating it as check would let the opponent capture the king before you could answer; the only fix for that is to make the move illegal, which is what deadlocks.
D-008 — Turning every block cannot make the board look irregular
  • Date: 2026-09-13
  • Status: active — a fact, recorded so it is not rediscovered
  • Context: Luqman's stated goal was "so the chess board will be abnormal".
  • The fact: every 2x2 block of a checkerboard is L D / D L. A quarter turn makes it D L / L D. Turning all sixteen therefore flips all 64 squares and leaves a perfectly regular checkerboard with light and dark swapped — the board's colours alternate each move and never become irregular.
  • Consequence: the disorder is entirely in the piece positions. Worked out before building and reported up front, so the mechanic was not sold on something it cannot do. If a visually irregular board is ever the goal, only a subset of blocks can turn — which is a different mechanic, not a tweak.
D-009 — Pawns are frozen by the twist
  • Date: 2026-09-14
  • Status: reversed 2026-09-14 — superseded by D-014. Wrong reading of the rule. Keep the observation that started it (the pawn's move options were already correct; the marker rendered exactly one square above it) — that part still holds and is now asserted permanently.
  • Context: Luqman: "if the player first turn is moving a pawn forward, after the board rotate and the opponent finished their turn, the pawn still can move forward, not left or right or back. fix that"
  • What was actually wrong. The pawn's move options were already correct — traced it: after a push and two twists the pawn on f4 could only play f5, and the move marker rendered directly above it (dx 0, dy −82.9px, exactly one square). What was wrong was the carry: the rotation dragged pawns sideways and backwards. e2→e4 became f4 and then f3 — behind where it started. That is what "left or right or back" was describing.
  • Decision: a pawn is never carried. It holds its square while the rest of the block cycles around it.
  • Why it does not break the mechanic: the pieces cycle among whichever of the four squares are not holding a pawn, in the same cyclic order. Still a bijection, so a twist still cannot capture and never has to resolve a collision. Two pawns in a block → the other two swap; three → nothing moves.
  • A rule it deletes: a frozen pawn can never be carried onto the last rank, so promotion-by-twist cannot happen and that code came out (D-006 had it).
  • Also simpler: the set of pawn-occupied squares is invariant under a twist, so the inverse computes the same free set and undoes it exactly — no need to record the permutation in the undo entry.
  • Consequence: the game plays much more like chess. Pawn structure survives and only the pieces get shuffled. Early on that means the back ranks swap pieces in pairs, since a block of two pawns plus two pieces reduces to a swap.
D-010 — The twist is the game, not a checkbox
  • Date: 2026-09-14
  • Status: active
  • Context: Luqman: "doesnt have to be a check box to make it rotate, it's the default game, it is not a regular chess."
  • Decision: the Twist toggle is gone from the UI and the twist is always on. newGame sets game.twist = true unconditionally.
  • Kept: the engine's twist flag itself, which defaults to off in the constructor. That is what lets the perft suite prove the plain rules engine is untouched, and what the standard-chess rule tests (castling, en passant, promotion) switch off deliberately — en passant cannot arise under the twist, so those cases would be untestable otherwise. It is a test seam, not a player setting.
D-011 — Two-player mode lives in the Opponent select
  • Date: 2026-09-14
  • Status: active
  • Context: Luqman asked for a two-player mode.
  • Decision: hotseat, both sides from one keyboard, added as the first option of the existing Opponent select (Two players, then four computer strengths). Choosing it hides the You play row, since with both sides human there is no colour to pick. Switching between the two modes starts a new game; switching between computer strengths does not, so difficulty can change mid-game.
  • One predicate, not scattered comparisons. Every place that used to ask game.turn === playerColor now asks humanPlays(game.turn). In hotseat that is always true, which is what stops the search ever running: aiTurn bails on humanPlays, so there is no second guard to keep in sync. playerColor survives only to say which way up the board starts.
  • Undo differs by mode, deliberately. Against the computer one undo takes back two plies so it is your turn again; in hotseat one ply is one turn, so it takes back one.
  • No auto-flip between turns. Tempting for hotseat, but the board already turns a quarter every move and spinning it 180° on top of that would be disorienting. Flip stays manual.
  • No new checkbox. Following D-010: the mode belongs in the select that already existed, not in another toggle.
D-012 — The fold slider is gone
  • Date: 2026-09-14
  • Status: active
  • Context: Luqman: "get rid of fold 45 degree slider."
  • Decision: the slider and its wiring are removed. The fold itself stays — the board still blooms open at the start of a game, closes into play, and blooms again when the game ends. What went was the manual control, not the mechanism.
  • Note: THETA_OPEN, animateTo and the whole hinge constraint are still load-bearing for those animations, so geom_check.js still earns its place. The controls panel is down to three rows: Opponent, You play, buttons.
D-013 — Animate each piece to its real destination, not by 90°
  • Date: 2026-09-14
  • Status: active
  • Context: Luqman: "when a piece already move forward and the board rotates, make the piece follow the rotation of the board, in the current game, the piece rotate with the board and then go back to its initial place."
  • The bug, and it was mine. The sweep rotated every piece 90° about its tile centre. That was correct while the twist was a plain quarter turn, and stopped being correct the moment pawns were frozen (D-009): the pieces then cycle among only the free squares, so a destination can be a quarter, a half or three quarters round — and a pawn's is zero. A 90° sweep therefore ended somewhere that was not the piece's square, and it jumped to the right one when the animation finished. On a frozen pawn it was unmistakable: swing out, snap back. Exactly what Luqman described.
  • Decision: sweep each piece by the actual angle from the square it came from to the square it is on. Both are cell centres of the same tile and so the same distance from its centre, which means a pure rotation lands exactly — no fudging, no snap.
  • Direction: always the way the tile turns, by normalising the angle to [0, 2π). A two-cycle between adjacent squares therefore sends one piece a quarter and the other three quarters; they never collide, and both follow the tile.
  • How it was missed: the earlier tests checked board state and paint angle, never where a piece was drawn. The position maths is now its own method, piecePosition(sq, now), and the suite samples it at the start, middle and end of a sweep. That is the test that would have caught this on day one.
D-014 — The carry is uniform: every piece turns one cell, pawns included
  • Date: 2026-09-14
  • Status: active
  • Context: Luqman: "the pieces should follow the rotation and stay. for example initial pieces location is a4, then the board rotate to the right, the pieces should now be at b4."
  • Decision: back to the plain quarter turn for everything. a4 → b4, a1 → a2 → b2 → b1 → a1, one cell round the block, pawns included.
  • Why D-009 was wrong. Freezing pawns forced the cycle to skip occupied squares, which is what broke his example: a piece on a4 with a pawn on b4 was shunted diagonally to b3 instead of simply turning to b4. The mechanic became hard to predict — the destination depended on which squares in the block happened to hold pawns — and a frozen pawn conspicuously failed to "follow the rotation" at all.
  • His pawn rule still holds, and is the right way round. A pawn only ever moves forward — never sideways, never backwards — wherever the board carries it. That was always true of the engine; it is now asserted for every pawn move in every position across a whole game, so it cannot regress silently. The board carrying a pawn is not the pawn moving.
  • What came back with it: promotion-by-carry (a pawn carried onto the far rank becomes a queen), and the undo record that reverses it.
  • What went away: the free-set machinery, its scratch buffers, and blockBase. Search went from 586k back to 803k nps, since the plain 4-cycle is four writes rather than a scan plus a rotation.
Lesson across D-009 and D-014

Three passes on the same sentence, and the cost each time was interpreting a reported symptom as a specified rule. What settled it was Luqman giving a concrete before/after — a4 then b4 — which is checkable in one line and leaves nothing to read into. Worth asking for that shape of example early when a rule is in doubt, rather than choosing between readings and building.

D-015 — Stop turning: three stops each, covering your move and the reply
  • Date: 2026-09-15
  • Status: active
  • Context: Luqman: "add a button to stop rotate for 1 round ... when white turns to make a move, white can choose to stop the rotate but the effect will on for black too for only that round ... after white turn again, the board rotate normally." Settled with him before building, as concrete move sequences rather than prose (the lesson from D-009/D-014):
    • Length: always two moves — the presser's move and the reply, whoever presses. White: e4 (no turn) ...e5 (no turn) Nf3 (turns); Black: ...e5 (no turn) Nf3 (no turn) ...Nc6 (turns). Chosen over "until the end of the White+Black round", which would give Black's stop one move.
    • Uses: a few per game → 3 each (STOPS_PER_GAME in js/main.js).
    • Who: both sides.
    • Computer: uses stops itself and plans around yours.
  • Added by me, flagged to him: a stop cannot be pressed while one is running (so they never chain), and undo gives a spent stop back.
  • Engine shape: a stop is the move with an F_STOP flag, not a separate action — one move stays one undo record, and search compares "Nf3" with "Nf3 + stop" for free. State is stopsLeft[2] and stopPlies, both saved in the undo record and both part of the repetition key. stopsPerGame defaults to 0 in the engine, like twist, so every older suite is untouched.
  • Search: unused stop valued at 100 cp. At 35 cp it stopped on move one: the piece-square tables are plain chess, so a board that stops turning keeps pieces where they "look" good. Stop moves are generated only in the first 2 plies of search — doubling the whole tree dropped strong from depth 4 to 3; limited to 2 plies it is back to 4. Deeper, a running stop is still played out exactly; only pressing a new one is not considered.
  • Known character: in club self-play the computer still takes its first stop early (ply 2 in 3/3 games). One inspected game was a losing side using stops defensively to keep its exposed king from being carried — legitimate, not a bug. Worth watching in real play.

04-methods.md · 22 sections

Methods

Verify a mechanism numerically before drawing it

The rotating-squares constraint was derived, then checked in plain Node before any rendering code existed: for every θ, assert that the nearest corner of each neighbouring tile pair coincides. test/geom_check.js reports a worst-case gap of ~1e-15 of the tile edge, and the same assertion runs again in the browser against real screen coordinates (~1e-13 px).

This is worth repeating for anything kinematic. A fold that looks right at the two end states is usually wrong in between, and a numeric assertion catches it in seconds instead of after the art is finished.

Perft is non-negotiable for a chess engine

test/perft.js counts leaf nodes against the six published reference positions (start position to depth 5 = 4,865,609; Kiwipete; positions 3–6). All 26 counts match. These positions exist specifically to catch en-passant legality, castling through check, pinned pieces, discovered checks and promotion — the bugs that otherwise surface as a wrong move six months later.

Let the test derive the answer, not the author

The first tactics suite failed three cases, and all three were bad test positions — one asked for Qxh4 from d1, which is not a queen move. Rewritten so the test finds every mating move using the already-perft-proven generator and only then asks the search to find one. A test that encodes my own analysis tests my analysis.

source-atop is canvas-wide, not shape-wide

Shading a canvas shape with globalCompositeOperation = 'source-atop' composites against everything already on that canvas, so a highlight gradient meant for one piece smeared bright columns across the whole board. The fix is also the fast path: draw the shape into its own offscreen canvas, where the only destination pixels are the shape itself, then blit. Same for ctx.filter = 'blur()' — bake it once into a sprite rather than running it per frame.

Walk a lathe profile in one direction

Building a symmetric silhouette by mirroring a profile: go up one flank, across the top, down the other, and let closePath lay the base. Traversing the profile in the wrong order self-intersects the path, and the stroke then draws a spurious diagonal across the piece — a subtle artifact that survived several looks because the fill still came out roughly right.

Drive the real UI with CDP, no dependencies

test/cdp.js is a ~90-line Chrome DevTools Protocol client built on Node's built-in WebSocket (Node 26). It launches headless Chrome, evaluates JS in the page, dispatches real mouse clicks at computed square centres, and captures screenshots. That is what let the browser suite test castling, promotion, en passant, undo and checkmate through actual clicks, and what let the artwork be inspected rather than assumed.

./test/run.sh          # geometry, perft, search, then the browser suite
Guard deferred work with an epoch counter

The AI turn and the end-of-game bloom are both scheduled with setTimeout. A timer from a finished game fired into a freshly set-up one and moved for the player. Every deferred action now captures a module-level epoch that a new game increments, and bails if it no longer matches.

Rotating a board means rotating the input, and shrinking it

Two things bite when you spin a playable board:

  1. The inverse transform. Screen coordinates have to go back through the rotation before they mean anything. Keep the rotation as a transform on the way out (applySpin) and invert it on the way in (applySpin(..., -1)), rather than folding quarter turns into the file/rank mapping — the mapping already carries flipped, and stacking the two is where bugs live. Test the inverse at every quarter and with the flip on.
  2. The bounding box grows. A square of side L at angle φ needs L·(|cos φ| + |sin φ|), so 1.41× at 45°. Anything already filling most of its frame will clip mid-turn. Scaling by min(1, margin/(|cos φ|+|sin φ|)) costs nothing at the rest positions and reads as a deliberate lift.
Make a transition atomic, or input leaks into the gap

The turn was first written as sleep(190) and then start the rotation, so the piece could land before the table moved. For those 190 ms the board looked completely settled — flat, no tween — and the interaction gate re-opened. The fix was to create the tween immediately with a start delay baked into its t0, and clamp t low as well as high in the loop. The gate is false for the whole transition, and the pause still happens.

The test suite found this, twice, before a person could: both a player-side and an AI-side settle() returned early in exactly that window.

An unbounded search extension is a latent crash

negamax had the standard if (inCheck) depth++ check extension. In plain chess it terminates by itself — you cannot stay in check indefinitely. Under the twist you can: kings are carried around every move, so check recurs, the extension fires at every level, depth never falls, and the search runs until the stack dies. The bug was always there; the variant just made it reachable.

Any extension needs a ceiling that does not depend on the rules being searched: an absolute ply cap that returns an evaluation, a cap on quiescence depth, and extensions allowed only so far past the current root depth.

Decide legality by what keeps the game playable, then measure it

Two rules were available for a forced board mutation:

  1. your move must leave your king safe after it, or
  2. the mutation stands down when it would expose your king.

(1) is more principled and came free with the existing legality test — and it deadlocked, drawing by stalemate on move 3. (2) keeps normal chess legality exactly, which is a property worth asserting directly: compare legalMoves() against a clone with the variant off, across a whole game. If they ever differ, the mechanic can take moves away from the player, and a freeze is possible.

Runtime.evaluate awaits promises, so void the ones you are timing

s.eval uses awaitPromise: true. An animation method that resolves on completion will therefore block the evaluate call for the full duration, and every screenshot afterwards lands after the animation finished — which is exactly what made a "mid-twist" capture come back showing a settled board. void view.twistOnce(...) returns undefined, so the call returns immediately and the capture is genuinely mid-flight. Assert the phase you think you caught (alpha between 5 and 85 degrees) rather than trusting the timing.

Separate what turns from what does not

The tile carries the printed checkerboard, so it turns with the twist. The square markers — selection, last move, check, legal-move dots — belong to board positions, which do not turn. Drawing both in one transform is wrong, and at rest it is invisible, because the two differ by a multiple of 90° and the cells line up either way. It only shows mid-animation. Two transforms: paintRot for the tile body, gridRot for anything that means "this square".

Likewise, pieces are positioned by the square they came from during a twist — make has already moved them on — and swung about the tile centre. At a quarter turn the arc lands exactly on the new square, which is worth deriving rather than tuning: rotating the local offset (u-0.5, 0.5-v) by +90° gives (v-0.5, u-0.5), the offset of (v, 1-u), for the flipped board as well as the unflipped one.

A test harness that spawns a browser must also reap it

test/cdp.js spawned a headless Chrome on every run and never closed it. After a dozen runs the orphans wedged the debugging port and the browser suite hung for minutes with no output — which looks exactly like a slow test, not a leak.

Three fixes, all cheap and all worth doing from the start:

  • launch() probes the port first and reuses a live browser instead of spawning a second one.
  • each Session remembers its target id and closes its own tab on the way out.
  • run.sh reaps the browser after the suite (pkill -f remote-debugging-port=...).

The general point: any harness that starts an external process needs the teardown written at the same time as the startup, because the failure mode is silent accumulation and the symptom shows up somewhere unrelated.

Headless Chrome will happily test code you edited minutes ago

The browser suite reported a pawn being carried that the engine demonstrably did not carry — the same scenario passed in node and failed in the browser. The browser was running cached JavaScript. Making launch() reuse a long-lived browser (to stop leaking one per run) turned this from occasional into near-certain.

The fix belongs in the harness, not the tests: create the target on about:blank, send Network.enable and Network.setCacheDisabled, and only then Page.navigate to the real URL. Navigating first and disabling the cache afterwards is too late — the page and its scripts are already fetched.

The tell was a node test and a browser test disagreeing about the same deterministic function. When that happens, suspect the harness before the code.

Trace the thing the user described before changing the rule

Luqman reported a pawn moving "left or right or back". Two readings: its move options were wrong, or the board was carrying it. Rather than guess — having already misread him once — I traced his exact sequence and printed, per ply, where the pawn stood, which directions it could move, and where the rotation put it. The same trace also caught three bad assertions of my own in a row: a pawn can legitimately change square by being played, by being captured, and its path can legitimately be blocked. An invariant about "nothing else may move it" has to exempt all three, or it fails for the right reasons and looks like a bug.

A [hidden] attribute loses to any class that sets display

Hiding a control row with el.hidden = true did nothing: the user agent's [hidden] { display: none } is beaten on specificity by .row { display: flex }. It needs an explicit .row[hidden] { display: none; }.

Assert the computed style rather than the attribute in the test — hidden === true passes happily while the element is still on screen, which is exactly the bug the test exists to catch.

Replace a scattered comparison with one predicate

Two-player mode touched nine places that all asked game.turn === playerColor in slightly different ways. Rather than add a mode check beside each one, they all became humanPlays(game.turn). The search then cannot run in hotseat for a structural reason — aiTurn bails on the same predicate — instead of because a second guard was remembered in every branch.

"Did it last long enough" is the wrong proxy for "is it playable"

The self-play test asserted plies > 20 to mean the game had not deadlocked. It then failed on a perfectly good 12-ply checkmate. The property actually worth holding is that games reach a legitimate result and that none dies in an early draw — which is the failure the mechanic could genuinely cause. Rewritten to run three games and report each outcome: checkmate@57, checkmate@52, checkmate@35.

Animation correctness needs a testable position function

The twist animation was wrong for weeks-worth of changes and every test passed, because the tests checked board state and the paint angle but never where a piece was drawn. A rendering bug hides from assertions about data.

The fix was to pull the maths out of the draw loop into piecePosition(sq, now) and assert on it directly: at the start of a sweep every piece must sit on the square it came from, at the end on the square it is on, and a frozen piece must not move at any sampled point. Those three checks are cheap, need no pixels, and catch the whole class — including "it looks fine then snaps at the end", which is invisible in a screenshot and obvious in a game.

When an invariant changes, re-derive everything that assumed it

The 90° sweep was correct when the twist was a plain quarter turn. Freezing pawns silently invalidated it, because the permutation stopped being a rotation. The constant 90° was the assumption, written down nowhere. Freezing was later reversed, so 90° is right again — but the code now derives the angle from the two squares, which is what makes it survive the next change to the rule.

Compute a quantity from the things it actually relates rather than hard-coding the value it happens to take. It costs a line and removes a whole class of silent breakage.

Ask for a before/after, not a better description

Three passes were spent on one rule about pawns and rotation, and every pass made the same mistake: reading a reported symptom as a specified rule. "the pawn still can move forward, not left or right or back" can mean the pawn's move options or the board dragging it, and I picked wrong twice.

What settled it in one line was a concrete before/after: a4 → b4. That is checkable, has no interpretation in it, and became a test the same minute. When a rule is genuinely ambiguous, asking for one example of the state before and the state after beats any amount of further prose — including from me.

The rule that had to change

First attempt was the principled one: your move must leave your king safe after the twist, enforced free by the existing legality test. It deadlocked — drew by stalemate on move 3. The permutation does not depend on your move, so a king boxed in by its own pieces is carried onto the same square every time, and if that square is covered every move is illegal. Dumped the position instead of assuming a bug:

8 r n b . k b n R      White to move, not in check, zero legal moves.
7 p p p p p p p p      King on e1, boxed in by its own pieces.
4 . . . q . . P .      e1 always carries to e2.
1 R N B Q K B N .      Black queen d4 always carries to d3, which covers e2.

So the twist yields instead of the player (D-007): it does not turn on a turn where it would expose your own king. Normal chess legality is then exactly untouched, which is asserted against a twist-free clone across 160 positions — that invariant is the thing that guarantees no freeze. It stands down on about one turn in seven.

A latent crash the variant exposed

if (inCheck) depth++ — the standard check extension — has no ceiling. In plain chess it terminates because you cannot stay in check forever. Under the twist kings are carried about constantly, check recurs, depth never falls and the search ran until the stack died. The bug was always there; the variant made it reachable. Now capped three ways: absolute ply, quiescence depth, and extension slack past the root depth.

Tests that caught my own mistakes

  • Two assertions failed while printing the right answer, because they raced the AI's reply. Fixed by measuring settled state, tying the paint angle to the engine's own record of which turns twisted, and stubbing aiTurn (a writable global in a classic script) for the one case that had to be isolated.
  • A "mid-twist" screenshot came back showing a settled board: Runtime.evaluate awaits promises, and twistOnce resolves on completion. void it.
  • An early assertion assumed the twist would make fewer moves legal. It makes more at first — a twist can rescue a king from check too. Wrong assumption, right code.

Where it ended

17 engine tests, 11 browser tests, plus the untouched 26 perft and 8 search. Self-play runs 85 plies and ends in checkmate. The twist gave check on its own in a real round (e4* Bd5+*).

A leak that looked like a slow test

The browser suite hung for minutes with no output. Cause: test/cdp.js spawned a headless Chrome per run and never closed it, and after a dozen runs the orphans wedged the debugging port. Now launch() reuses a live browser, each session closes its own tab, and run.sh reaps the browser at the end. Worth remembering that a leak in a harness presents as a slow or flaky test somewhere else.

What came in

The fork

"Make this chess game" could mean a printable model or a playable game. Asked; Luqman chose the digital game (D-001).

Order of work

  1. Derived the mechanism first, before any rendering. d = a·√2·cos(45°+θ), checked numerically — worst hinge gap ~1e-15 of the tile edge.
  2. Rules engine, then perft. 26/26 published reference counts.
  3. Search — negamax, alpha-beta, quiescence, MVV-LVA, killers, tapered eval.
  4. Renderer, then artwork.
  5. Browser tests via a hand-rolled CDP client, so the artwork could be looked at rather than assumed.

Bugs found by actually looking

  • source-atop composites canvas-wide, so the piece highlight smeared bright columns across the whole board. Fixed by baking pieces into offscreen sprites.
  • lathePath walked the profile in the wrong order, self-intersecting the path; the stroke then drew a spurious diagonal across five of the six piece types. The knight was clean, which is what identified it.
  • 4 fps. ctx.filter = blur() per tile per frame. Baking the tile body, pin, shadow and backdrop into sprites took it to 54 fps.
  • A setTimeout-ed AI turn from a finished game fired into a new one and moved for the player. Now guarded by an epoch counter.
  • Three tactics tests "failed" that were my own bad positions — one asked for a queen move that does not exist. Rewrote the suite to derive mates from the proven generator instead of from my analysis.

Where it ended

Feature complete and tested: 26 perft + 8 search + 9 browser tests, all passing. Not committed — left for Luqman. Portfolio card added.

Later the same day — the table turns

Luqman asked for the board to rotate 90° after each move. Implemented as a transform on the way to the screen, with the click path inverted through it (D-005). Three things that were not obvious up front:

  • A rotating square's bounding box grows to 1.41× at 45°, so the corners clipped until the scale backed off mid-turn.
  • There was a 190 ms window after each move — the pause letting the piece land — where the board looked settled and input re-opened. Closed by baking a start delay into the tween instead of sleeping before creating it.
  • The search blocks the thread, so the turn has to finish before the engine starts or the rotation freezes halfway.

The spin suite is 8/8, and the earlier suites still pass once the rules tests turn the spin off — they are about chess, not the table.
